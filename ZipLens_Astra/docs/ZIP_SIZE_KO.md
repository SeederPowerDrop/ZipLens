# 작은 파일의 ZIP 용량 증가 검토 — 2026-09-08

## 결론

사용자가 제시한 `안내.txt` 40바이트 → `plain-check.zip` 158바이트는 정상적인 ZIP 형식 오버헤드다. 압축 내용은 40바이트이고 파일명·헤더·목록·종료 기록이 118바이트다. 이 사례에서 중복 저장이나 데이터 손상은 발견하지 않았다.

## 실제 파일 분석

`plain-check.zip`은 앞서 GUI 동작 확인을 위해 Python으로 만든 검증용 ZIP이다. 별도로 같은 내용을 ZipLens의 실제 압축 기능으로 만든 `안내.txt.zip`도 함께 조사했다. 두 ZIP 모두 다음 구성이었다.

| 구성 | 바이트 |
| --- | ---: |
| Deflate로 처리된 파일 내용 | 40 |
| 파일 헤더 30 + UTF-8 파일명 10 | 40 |
| 중앙 목록 46 + UTF-8 파일명 10 | 56 |
| ZIP 종료 기록 | 22 |
| 합계 | **158** |

- 원본 크기: 40바이트. 내부 파일: `안내.txt` 한 개.
- 압축 방법: **8 (Deflate)**. 압축 후 내용도 40바이트다. 크기가 같다는 이유로 무압축 저장 방식이라고 추정해서는 안 된다.
- UTF-8 파일명 플래그: 2048. 추가 필드·주석·데이터 디스크립터는 없다.
- 두 ZIP의 CRC 검사를 통과했고, 각각 해제한 바이트가 원본과 동일하다.
- 원본 SHA-256: `2cffafff5be7df83757c255789e7108b3e606cfba7db0be2d576f10c2b2bfeca`.

ZIP은 압축된 내용 외에도 각 파일의 이름과 복원에 필요한 기록을 저장한다. 이 구조는 [PKWARE ZIP 명세의 4.3.7, 4.3.12, 4.3.16](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT)에 정의되어 있다. 위 숫자는 해당 구조에 따라 실제 두 파일을 분석한 결과이며, 모든 ZIP의 부가 정보가 항상 118바이트라는 뜻은 아니다.

## 코드 검토와 개선 여지

`astra-core/src/compress.rs`는 동일한 아카이브 이름을 거부하고 출력 파일을 원본 내부에 만드는 것을 막는다. 일반 파일은 한 번씩 쓰고 원래 크기만큼 읽었는지 검사한다. 레벨 0은 Stored, 1–9는 Deflate이며 기본 레벨은 6이다. 이번 ZIP에는 불필요한 추가 엔트리가 없다.

현재 일반 ZIP 경로는 Deflate 결과가 더 커질 때 Stored로 자동 전환하지 않는다. 압축하기 어려운 입력에 대한 향후 최적화 후보이나, 이번 사례는 내용 크기가 늘지 않았으므로 해당 문제가 원인이 아니다. Stored로 바꾸어도 이 파일은 내용 40 + ZIP 부가 정보 118 = 158바이트다. 크기 증가만을 근거로 압축 실패로 표시하거나 형식 기록을 제거해서는 안 된다.

이번 작업은 실제 파일 구조·무결성·코드 검토이며 엔진 코드를 변경하거나 앱을 다시 빌드하지 않았다. 이 결과는 다른 입력·포맷·옵션의 모든 크기 증가를 검증한 것으로 확대 해석하지 않는다.
